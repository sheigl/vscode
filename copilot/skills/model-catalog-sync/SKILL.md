# Model catalog sync

One model, four places. llama-swap is the source of truth; everything downstream
is generated. Manual edits to the generated files are lost on the next run.

## The chain

| # | Where | What | Produces |
|---|---|---|---|
| 1 | ai.home, desktop2.home, server.home | `~/.config/llama-swap/config.yaml` | the served models (entry name + aliases) |
| 2 | **the gateway** (`$LITELLM_SERVER`, llm_router) | `POST /api/v1/providers/{id}/models/preview` then `…/models/sync`, one provider per machine | the served model list: one deployment per upstream model, metadata discovered from llama-swap, prune on a build that has it (see *When the gateway image lags*) |
| 3 | **ai.home** | `~/.config/opencode/scripts/gen_litellm_models.py` | `~/.config/opencode/opencode.jsonc`, commit + push |
| 4 | **ai.home** | `~/.config/Code/User/gen_vscode_models.py` then `… apply` | `models.json` (tracked, commit + push) and `chatLanguageModels.json` (machine-local) |
| 5 | **every other machine** | `git pull` over ssh, plus `gen_vscode_models.py apply` where `models.json` exists | the other machines match ai.home |

The machines are the `ssh` entries in `~/.config/opencode/scripts/config.json`,
so a new box is picked up by adding it there. The remote pull probes each one, so
a machine without VS Code gets the OpenCode pull only.

Both generators read `~/.config/opencode/scripts/config.json` for the per-model
`overrides` (context / output / vision) and `defaults`. Capabilities otherwise
come from each machine's llama-swap config (context from `--max-context`,
vision from a `--mmproj`, reasoning/effort from the chat template), with the
gateway's own fields as the fallback: `context_length`, `max_output_tokens`,
`traits` (vision / tools / reasoning), `input_modalities` and
`supported_parameters`. The gateway maps an alias to its machine through
`owned_by`, so a provider whose name is the machine's tailnet host is what makes
that lookup work.

## Run it

```sh
~/.agents/skills/model-catalog-sync/sync.py            # full chain
~/.agents/skills/model-catalog-sync/sync.py --dry-run  # report drift, change nothing
~/.agents/skills/model-catalog-sync/sync.py --no-vscode
```

Needs `LITELLM_SERVER` and `LITELLM_API_KEY` — the same master key the router
uses, despite the variable names. The gateway, OpenCode and VS Code steps stop
at the first failure; the remote pull (script step 6) is best effort per host
and makes the run exit non-zero if any machine failed. Step 2 skips a provider
whose llama-swap is unreachable or returns an empty inventory, because prune is
unconditional: syncing either would delete that machine's models. Every step is
idempotent, so re-running is always safe. The script finishes with a
before/after diff, a limit sanity check and the per-host result for the other
machines.

To skip the remote machines, set `MODEL_SYNC_REMOTE_HOSTS=` (empty). To target
just one, set it to a comma-separated list of ssh hosts.

The script accepts both plan shapes the API has used — counts (`additions`,
`updates`) with an `items` list carrying `action`, or the newer `added` /
`updated` / `removed` arrays — and both `revision` shapes (a number, or the whole
store snapshot the sync response can return). That is deliberate: the deployed
image and the source tree lag each other, and a sync run must not break because
of which one answered.

Use `--dry-run` first when you only suspect drift, and after any edit to
`config.json` overrides. It really checks now: it compares every llama-swap
endpoint against the gateway's `/api/v1/models` per provider (missing ids, ids
whose upstream model no longer exists, and aliases still without context or max
output), then runs both generators into a temp path and diffs the resulting ids
and limits against the live files.
It writes nothing and leaves both repos alone.

## When the gateway image lags the code

The sync API and the image serving it drift independently. Two symptoms mean the
running build predates the metadata and prune work; neither is a bug in this
script:

- `preview` returns `missing` as a list of **strings** (`["muse:30b", …]`) and
  the sync leaves those deployments in place. The current build returns
  `{id, alias, upstreamModel}` objects and deletes them.
- After a successful sync `GET /v1/models` still shows no `context_length`,
  `max_output_tokens`, `traits`, `input_modalities` or `supported_parameters`
  for the machine providers, so contexts keep coming from llama-swap flags and
  hand overrides, and the generators keep printing a long "Add real values …
  under 'overrides'" list.

Delete the leftovers by hand until the image is rebuilt (one call per id from
`GET /api/v1/models`; group memberships, AI-router routes and key scopes cascade
with it):

```sh
curl -X DELETE "$LITELLM_SERVER/api/v1/models/mdl_..." -H "Authorization: Bearer $LITELLM_API_KEY"
```

then run `sync.py` again to regenerate the clients. The two counts differ on
purpose: `/v1/models` lists the deployments **plus agents** (`clyde`, `oracle`),
so 87 deployments can be 89 served ids.

## Editing llama-swap

An entry is not removed by deleting it alone:

1. comment the model block (keep the name, note the date and reason),
2. comment its routing var under `routing.router.settings.matrix.vars`,
3. comment any `sets` expression that names it — a set member with no routing
   var fails validation,
4. re-check: `python -c "import yaml; yaml.safe_load(open('config.yaml'))"`, no
   unresolved vars, no dangling set members.

llama-swap runs `--watch-config`: the change is live in seconds and the models
list updates without a restart. A resident model (`ttl: 0`) keeps running.

Every alias also becomes its own served id (`includeAliasesInList`), so an
override usually has to be written for the canonical id *and* for the aliases
that clients still use.

## Overrides (`scripts/config.json`)

Keys are `<machine>.<served id>`, e.g. `desktop.qwen3.8-flash-next:Q4_K_M`.
Lookup is exact first, then with the quant suffix stripped
(`desktop2.flint:q4` → `desktop2.flint`).

```json
"desktop.qwen3.8-flash-next:Q4_K_M": { "context": 200000, "output": 32768, "vision": true }
```

Renaming a model in llama-swap **breaks its override silently** — that is the
most common cause of a broken catalog. Check for `Overrides matching no model`
in the generator output and prune or re-key those entries.

## Failure modes seen in practice

| Symptom | Cause | Fix |
|---|---|---|
| OpenCode compacts on the first turn | `limit.input` is 1 (or tiny) | add an override with `output`; the generator also guards `output >= context` now |
| `input: 1`, `output: 200000` | no override, and the gateway reported a max output equal to the context | override `output` (e.g. 32768); the router never derives output from context, so this should only come from a hand-set value |
| Model in the gateway but 404s from llama-swap | the gateway is one sync behind | run `sync.py` |
| `sync.py` prints `-0` while `preview` listed ids under `missing` | the running image does not prune yet | `DELETE /api/v1/models/{id}` by hand, then `sync.py` (see *When the gateway image lags*) |
| A catalog entry has no `limit` block | its upstream is gone and the build did not prune it | delete the deployment, then `sync.py`; the generator cannot size a model it cannot map |
| Model missing from the gateway | llama-swap entry parked/renamed, or the provider was skipped (unreachable) | run `sync.py`; check the entry is not commented and the machine is up |
| `sync.py` prints `skipped: unreachable` / `empty inventory` | step 2 will not prune a machine it cannot read | bring that llama-swap up and re-run; the other providers were still synced |
| Model in OpenCode but not in VS Code | step 6's `apply` failed, or that machine is offline | fix the host, re-run `sync.py`; manual `uv run gen_vscode_models.py apply` there |
| Step 6 prints `FAILED` for a host | ssh unreachable, or its checkout has local edits to a pulled file | fix the host/checkout, re-run `sync.py`; the other steps are no-ops |
| Embedding/reranker ids listed as "not generated" | they are deliberately skipped (not chat models) | ignore |
| Overrides reported as matching no model | the model was parked or renamed | prune them, or re-key |
| `--dry-run` lists `+ desktop.id` / `+ server.id` | the model is live in llama-swap but the gateway has not been synced | run `sync.py` |
| `--dry-run` lists `- desktop.id` | a deployment's upstream model is gone (a rename left it behind) | run `sync.py`: prune removes it, and group/key scopes cascade |

## Verify before saying it is done

- `sync.py --dry-run` says `ok: every llama-swap id is in the router` and
  `(no change)` for OpenCode and VS Code
- `limit sanity` says ok, and the models you touched print plausible context/input/output
- the model is reachable end to end: `curl $LITELLM_SERVER/v1/models` contains
  the `desktop.*` / `desktop2.*` / `server.*` id, a one-line completion through
  that id works, and `GET /v1/models/<alias>` reports its `context_length`
- step 6 lists every other machine as `ok`; anything marked `FAILED` still needs
  its pull/`apply` by hand, then a re-run
